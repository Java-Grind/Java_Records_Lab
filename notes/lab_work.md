# Java Records — лабораторная

## Цель

На коде понять, когда record точнее обычного класса для данных: что генерирует компилятор, где проверять инварианты, как records ведут себя в коллекциях и почему их удобно сочетать с sealed interface и pattern matching.

## Карта понятий

    Компоненты record
            │ компилятор генерирует
            ▼
    Конструктор + accessors
            │ value semantics
            ▼
    equals / hashCode / toString
            │ можно использовать в Map и Set
            ▼
    Неизменяемый носитель данных

- Record — класс, декларация которого задаёт состояние как компоненты.
- Accessor — метод с именем компонента, например name().
- Compact constructor — конструктор для проверки и нормализации компонентов.
- Value semantics — равенство зависит от значений компонентов.
- Sealed interface — ограниченный набор разрешённых реализаций.

## 1. Record убирает шаблонный код данных

Код: [Lab_Main.java](../src/main/java/org/Lab_Main.java).

| Обычный data class | Record |
| --- | --- |
| Поля, constructor, getters пишутся вручную | Компоненты указаны в заголовке |
| equals, hashCode, toString нужно поддерживать | Генерируются из компонентов |
| Больше места для расхождения | Меньше шаблонного кода |

Record не делает объект автоматически глубоконеизменяемым: если компонент содержит изменяемый List, сам список всё ещё можно менять.

### Мои выводы

> Record хорошо выражает маленькое значение с понятным набором данных.

> Меньше кода не означает меньше ответственности за модель данных.

## 2. Compact constructor защищает инварианты

Код: [Validation_Main.java](../src/main/java/org/Validation_Main.java).

| Вход | Результат |
| --- | --- |
| Пробелы и верхний регистр | Нормализованный email |
| Строка без @ | Понятное исключение |

В compact constructor компоненты уже доступны по именам. Присваивание value меняет значение, которое уйдёт в неявное поле record.

### Мои выводы

> Валидацию лучше поставить на границу создания значения.

> Нормализация в constructor делает все экземпляры согласованными.

## 3. Record patterns и закрытая модель событий

Код: [PatternMatching_Main.java](../src/main/java/org/PatternMatching_Main.java).

| Элемент | Роль |
| --- | --- |
| sealed Event | Ограничивает допустимые события |
| records | Описывают данные каждого события |
| switch с pattern | Разбирает вариант и компоненты |

Компилятор проверяет полноту switch для sealed иерархии. Если появится новый разрешённый event, обработку нельзя случайно забыть.

### Мои выводы

> Sealed + record хорошо подходят для конечных наборов сообщений и состояний.

> Pattern matching делает извлечение данных частью читаемого ветвления.

## 4. Value semantics в Set

Код: [Collections_Main.java](../src/main/java/org/Collections_Main.java).

| Добавление | Размер Set |
| --- | --- |
| Coordinates(10, 20) | 1 |
| Ещё раз Coordinates(10, 20) | 1 |
| Coordinates(20, 10) | 2 |

Сгенерированные equals и hashCode делают record естественным ключом Map или элементом Set, если его компоненты сами корректно сравниваются.

### Мои выводы

> Два record с одинаковыми компонентами равны по значению.

> Это удобно для DTO, ключей и маленьких доменных значений.

---

## 5. Границы records

| Ситуация | Подход |
| --- | --- |
| DTO, событие, value object | Record — хороший кандидат |
| Много изменяемого состояния и сложный lifecycle | Обычный класс |
| Нужна наследуемость от класса | Record не подходит: он final |
| Компонент — mutable collection | Сделать defensive copy |

Record — это обычный class с конкретной моделью, а не замена всем классам проекта.
